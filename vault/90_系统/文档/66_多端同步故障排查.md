# 多端同步故障排查

本文面向第一次使用 kos 的用户。正常同步只需要 kos Companion、一个私有 Cloudflare R2 Bucket 和同一份加入码；不需要安装 Self-hosted LiveSync，也不需要理解 Journal、chunk 或 checkpoint。

## 先确认四件事

1. 第一台设备是内容完整的源 Vault，第二台设备是准备加入的本地 Vault。
2. iPad Vault 位于“在我的 iPad 上”，不是 iCloud Drive 中的另一个同名 Vault。
3. 两台设备都只启用 kos-sync；不要同时使用 iCloud、Obsidian Sync、Syncthing、Git 自动双向同步或其他同步插件。
4. 排查期间把 Obsidian 保持在前台，不要在两端继续编辑同一个文件。

先在两端打开“kos 驾驶舱 → 系统 → 多端同步”，记录当前状态、最后尝试、最后成功、待上传、待应用和冲突数。需要立即确认时，先在源端点“立即双向同步”，成功后再在目标端点一次。任一端显示“已同步”只说明该设备完成了检查，不能代替另一端的最后成功时间。

## 插件没有出现或显示加载失败

- 确认插件目录是 `.obsidian/plugins/kos-companion/`，该目录根部直接包含 `manifest.json`、`main.js` 和 `styles.css`，不能多套一层目录。
- iPad 应安装发布包中的 `kos-companion-mobile`；不要把桌面包中的 `kos-agent/` 当成移动端依赖。iPad 不运行本地 kos-agent，也不需要 Node.js。
- 在“设置 → 第三方插件”关闭 Restricted Mode，并手动启用 kos Companion。iPadOS 不允许安装器绕过这次安全确认。
- 覆盖插件文件后，彻底退出 Obsidian再打开。仅返回 Vault 列表不一定会重新加载 `main.js`。
- 若仍失败，不要改装旧版插件。记录 Obsidian 版本、kos Companion 版本、设备型号和屏幕上的完整错误信息。

正式面向普通用户发布前，应通过 Obsidian 社区插件或受支持的测试发布渠道安装。开发阶段的 USB 写入只用于真机验收，不是最终用户流程。

## 加入码提示无效、不完整或已损坏

加入码必须是以 `KOS-SYNC1.` 开头的一整行文本。它包含未加密的 R2 凭据，长度会随凭据变化，不能分段复制。

1. 回到源端 kos Companion 设置，重新点击“复制本机加入码”。
2. 在 iPad 点击“从剪贴板加入”；系统询问时选择允许粘贴。
3. 若出现输入窗口，长按输入框粘贴。窗口会显示实际字符数。
4. 不要从聊天气泡、截图 OCR 或换行后的预览中分段选择加入码。
5. 仍失败时重新生成并复制，不要手工修补 Base64 字符串。

加入码被发到聊天、邮件、工单或公开截图后，应在 Cloudflare 撤销或轮换对应 R2 凭据；只清空剪贴板不能让已泄露的加入码失效。

## R2 无法连接

kos 设置中只填写以下四项：

- Cloudflare Account ID：32 位 Account ID，不是完整 endpoint；
- R2 Bucket：私有 Bucket 名称；
- Access Key ID；
- Secret Access Key。

Cloudflare 页面显示的 Token value 不填入 kos。Token 权限应限制为目标 Bucket 的 Object Read & Write。检查设备时间、网络和 Bucket 是否仍存在；不要为了连通而把 Bucket 改成公开。

填写后点击“测试 R2 读写”，按提示区分认证失败、权限不足、Bucket 不存在、网络或超时。测试会在当前 Vault 的 `_preflight/` 隔离路径写入、读回并删除随机对象，不会修改同步 Journal。测试失败时同步不会启用；不要通过跳过测试、公开 Bucket 或换同步引擎来绕过。若配置有任何变化，重新测试再连接。

## 显示“已同步”，但目标设备没有内容

按固定顺序处理：

1. 在源端确认打开的是正确 Vault，而不是测试副本、旧目录或 iCloud 中的同名 Vault。
2. 源端点击“立即双向同步”，等待状态重新变为“已同步”。
3. 再在目标端点击“立即双向同步”，保持前台直到完成。
4. 检查最后成功时间是否确实更新，而不是只看状态文字。
5. 若浏览器存储或 Obsidian profile 被重建，kos 会检测空 IndexedDB 与旧 checkpoint 的不一致，并执行安全的远端优先重建。不要手动删除 `sync-state.json`。

如果源端本身没有完成第一次上传，第二台设备只能加入一个空同步空间。不要复用开发测试结束后已经清理的加入码。

## 只有 `10_收件箱`、`80_Skills`、`90_系统`，中间目录缺失

kos 的空目录由 `.gitkeep` 表示。旧版同步只读取 Obsidian 可见文件时会漏掉这些隐藏占位文件，表现为有正文的目录出现、空目录消失。

1. 两端更新到包含隐藏文件同步修复的同一版 kos Companion。
2. 源端彻底重启 Obsidian并点“立即双向同步”。
3. 目标端彻底重启并点“立即双向同步”。
4. 确认 `00_工作台`、`11_原材料`、`12_信息雷达`、`20–42` 等目录恢复。

不要在 iPad 手工补一套同名目录来掩盖问题；这会让真正的源端上传缺陷继续存在。

## iPad 没有自动更新

iPadOS 挂起 Obsidian 后不保证后台同步。把 Obsidian切回前台，在驾驶舱点击“立即双向同步”，并等最后成功时间更新。切换 Wi-Fi、蜂窝网络或 VPN 后也按此顺序重试。

如果每次只有手动同步有效，记录设备、iPadOS 版本、Obsidian 版本、前后台操作和时间点，作为移动生命周期问题报告；不要缩短同步间隔来耗电轮询。

## 出现 `.sync-conflict-*` 文件

冲突副本表示两端在未看到对方修改时编辑了同一路径，或删除与编辑同时发生。kos 保留副本是为了不丢内容。

1. 暂停两端同步。
2. 分别备份两个 Vault。
3. 比较主文件与 `.sync-conflict-*`，人工合并为唯一版本。
4. 删除确认不再需要的冲突副本。
5. 先恢复真相源同步，再恢复另一端。

不要批量删除所有冲突副本，也不要让 Agent在未比较内容时自动选择版本。

## 换了 Vault、重装 Obsidian或清除了应用数据

- 加入另一个同步 Vault 时必须使用该 Vault 的加入码；checkpoint 会按 Vault ID 隔离。
- Obsidian profile 或 IndexedDB 被清除后，kos 会从 R2 和当前 Vault 安全重建本地数据库。
- 重装前应备份 Vault 与 R2 凭据。R2 同步不是备份，误删除会传播到其他设备。
- 不要把旧 Vault 的 `sync-state.json` 手工复制到新 Vault。

## 必须停止并人工处理的情况

出现以下任一情况时，暂停两端同步，不要继续试错：

- 同一批文件反复删除和恢复；
- 冲突数持续增加；
- R2 凭据疑似泄露；
- Bucket 被清空或换成了错误的 Vault ID；
- 两端都包含无法自动判断的新内容；
- checkpoint 隔离失败或系统卡持续显示同一错误。

止损顺序固定为：两端暂停同步 → 停止编辑 → 分别备份 → 比较差异 → 选定唯一真相源 → 再执行重建。远端清空、指定设备覆盖其他设备和批量删除都不是普通排查步骤。

## 报告问题时提供什么

可以提供：

- 设备与系统版本；
- Obsidian 与 kos Companion 版本；
- 源端/目标端 Vault 名称；
- 系统卡状态、最后尝试、最后成功、待上传、待应用、冲突数；
- 完整错误文字和复现步骤；
- 缺失文件的相对路径。

不要提供 Secret Access Key、完整加入码、模型 API key、私密笔记正文或包含凭据的 `data.json`。
